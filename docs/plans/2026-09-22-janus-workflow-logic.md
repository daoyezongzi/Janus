# Janus 工作流逻辑改进方案

状态：技能规则、README 和元数据已实施；验证依据记录于 LOG，持续任务验收记录于 TODO。本次发布要求独立子代理审核通过、提交、push 和本机技能更新。

## Goal

明确三个技能的职责、进入条件、交接内容、返回位置和任务完成条件。执行根据当前用户要求与实际证据继续，流程投入由具体任务条件决定。

## Context / Constraints

- 以当前有效的用户请求确定目标、范围、限制和交付物；后续消息没有改变的要求继续有效。
- 保持 `brainstorming`、`developing`、`debugging` 三个技能。执行规则的规范来源为 `skills/developing/SKILL.md`。
- 规则采用自然语言，使用已有文件、工具和会话状态完成执行。
- 专业技能负责相应领域方法，Janus 使用其已确认的输入与产物，补充当前任务需要的工作。
- 每项流程步骤都需要明确的适用条件。任务请求本身可以是分析、设计、诊断、实现或实验。
- 本次交付包含本机三个 Janus 技能的更新，安装前保留原文件备份，并核对安装内容与通过审核的仓库文件一致。

## Design

### 技能职责与交接

| 技能 | 进入条件 | 负责的工作 | 交付与返回 |
| --- | --- | --- | --- |
| `brainstorming` | 存在会改变方案、范围、验收或下一项操作的未决问题 | 读取相关事实，形成决策；必要时确定能够回答问题的实验 | 返回决策、依据、约束、下一项操作及验收要求。用户只要求讨论时，完成所要求的设计交付即可结束 |
| `developing` | 用户要求实施、运行、评估或继续执行任务 | 保存完整目标，安排执行、验证、必要的技能调用和最终交付 | 根据全部适用要求及当前证据确认完成，或明确尚未完成的要求与限制 |
| `debugging` | 存在需要解释的可观察异常，或用户要求诊断 | 复现、取得证据、检查假设；在授权范围内修复已得到证据支持的缺陷并重新验证 | 返回诊断结论、证据、实际改动、复现结果和剩余问题；嵌入执行任务时返回受影响的原步骤 |

交接信息使用当前会话或已有 Working Plan。直接进入某个技能时，按照当前请求确定交付物；被执行任务调用时，保留原任务目标、当前步骤和剩余要求。局部问题得到处理后，继续完成原任务。

`brainstorming` 的完成条件是当前请求得到充分回答，或执行所需的决策已经确定。执行研究方案时，可以将取得区分性证据作为下一项操作，并提前确定观察结果对应的判断。

### 按任务条件选择措施

| 任务条件 | 对应措施 |
| --- | --- |
| 有影响执行的未决问题 | 使用 `brainstorming` |
| 实施涉及多个相互依赖的步骤，或需要说明设计与验证安排 | 使用相应详细程度的 Working Plan |
| 持续时间、任务跨度或预期会话边界使恢复记录有价值 | 将 Working Plan 保存在项目既有计划位置 |
| 失败影响较大，恢复困难，涉及关键行为或重要研究结论 | 增强前置检查、验证和适用的独立审核 |
| 并行工作需要保护不同修改范围或执行状态 | 使用有必要的工作目录隔离 |
| 存在可以分别取得证据、分别验收的独立任务 | 根据协作收益安排子代理 |
| 出现无法解释的运行结果 | 使用 `debugging` |

这些条件可以同时成立。设计明确的高影响任务采用相应的计划与验证要求；讨论围绕具体未决问题进行。流程说明使用上述条件表达，README 与技能中的执行路径采用相同判断。

### 执行过程与返回条件

执行开始时，读取当前事实，明确目标产物、允许修改的范围与验收要求，解决影响当前步骤的未决问题。按照已确定的安排执行，并检查实际结果。

| 检查结果 | 后续操作 |
| --- | --- |
| 当前步骤满足要求，原任务仍有剩余工作 | 继续下一项工作 |
| 观察符合当前复现或实验设计 | 根据预定判断继续诊断或分析 |
| 出现需要解释的异常 | 将预期结果、实际证据、复现条件和受影响步骤交给 `debugging` |
| 新证据改变了方法选择 | 更新执行安排；存在未决设计问题时进入 `brainstorming` |
| 缺少必要信息或执行条件 | 继续独立且已经授权的工作，说明受阻要求及必要条件 |
| 全部适用要求已有充分证据 | 完成适用的记录、成果检查和交付 |

诊断返回时，核查原任务的剩余要求。修复了执行过程中的某个问题，仅能确认该问题对应的检查结果。

### 诊断结果与研究完成条件

承担诊断判断的探查需要明确假设、预期观察、实际观察和执行是否有效。执行失败或观察不足时保留未确定结论。只有探查正确执行，且观察足以区分解释时，才能据此支持或否定假设。

| 诊断结论 | 后续操作 |
| --- | --- |
| 发现有证据支持的实现、数据、环境或测量问题 | 在当前授权范围内修复，重新运行原始复现及受影响检查 |
| 研究结果通过有效性检查 | 返回研究任务，按照研究问题与评价方法解释结果 |
| 当前证据不足 | 明确下一项能够增加证据的探查；执行条件不足时报告限制 |

重复探查没有增加证据时，重新检查假设、输入、测量方法和环境。纯诊断请求的交付条件由所需解释和支持证据决定。

研究任务分别定义实验有效性要求、需要回答的问题和结论所需证据。支持假设、否定假设以及明确证据局限均可构成研究结果。任务是否完成仍取决于用户要求与约定交付物；达到性能指标的请求必须依据该指标判断完成状态。评价标准的变更需要有需求或测量依据。

### 当前请求、计划、产物与恢复

| 信息 | 职责 |
| --- | --- |
| 当前有效用户请求 | 决定目标、范围、限制和交付物 |
| 上游 PRD、proposal、experiment brief | 提供当前仍适用的领域要求与已确认决策；编辑遵守明确授权 |
| Working Plan | 保存执行方法、验证安排和影响后续操作的决策 |
| 当前文件、数据和运行结果 | 判定实际进展、产物内容及证据适用范围 |
| LOG | 保存具有后续价值的结论与证据位置 |
| TODO | 保存依据当前要求与证据确认的剩余工作 |

用户改变要求时，识别受影响的步骤、产物和验证条件，更新允许修改的任务记录。继续编辑时读取当前文件，保留用户已作出的修改。事实与计划存在差异时核实进展；需求确实无法确定时再询问用户。

恢复长任务时，确认目标、限制、最近确认的成果、下一项操作、仍在运行的任务和剩余验证。已有上下文足以支持下一项操作时继续执行；涉及可能已经改变的文件、进程或实验输出时读取相关当前状态。持久记录提供必要的证据位置和版本信息。

### 验证、记录与交付

完成声明必须关联当前产物及相应证据，并明确检查实际覆盖的要求。相关代码、数据、依赖、配置或评价方法发生变化后，重新执行受影响检查。未受影响的结果可以继续使用。

只有整个请求的适用要求都得到充分处理，才报告任务完成。仍缺少必要验证时，报告已确认结果和具体限制。研究报告分别说明实现有效性、实验执行和研究结论。

记录与提交遵守任务允许的修改范围。只读工作通过会话或已有结构化状态保存进度。允许写入的工作在产生具有后续价值的决策、结果或剩余事项时更新现有 LOG/TODO，并以引用联系已有证据。

嵌入完整执行任务的技能返回已有成果，由 `developing` 统一完成适用的最终记录与交付。仓库提交继续按照现有条件执行，仅包含本任务允许保存、经过验证且可以安全分离的修改。

### 子代理与专业技能

委派子任务时说明具体问题、必要事实、文件修改范围、依赖关系、预期产物及验收证据。子代理返回可检查的结论或成果、验证结果及未确定事项。主代理核验关键结果并处理整合后的要求。

任务分配依据独立性及预期协作收益。专业技能已经完成的步骤通过其产物与证据确认，Janus 继续当前任务需要的工作。影响当前操作的真实矛盾需要解决，独立且已经授权的工作可以继续。

## Changes

| 文件 | 计划修改 |
| --- | --- |
| `skills/developing/SKILL.md` | 将条件选择、执行返回、当前要求与实际状态、证据适用范围及完整任务的结束条件集中定义；将三个固定风险流程改为条件表及简短适用示例；补充子代理交接要求 |
| `skills/brainstorming/SKILL.md` | 明确讨论请求和嵌入执行任务时的交付与结束条件；交接包括决策及验收要求；执行期间调用后返回原任务 |
| `skills/debugging/SKILL.md` | 增加缺陷、可信研究结果、证据不足三种处理；明确探查执行状态及返回原任务的位置；按诊断目标组织完成声明 |
| `README.md` | 同步职责说明、条件选择和执行流程中的返回分支，引用规范文件 |
| `skills/*/agents/openai.yaml` | 检查 `short_description` 与 `default_prompt` 是否准确表达各技能的适用条件，按需要同步 |
| `LOG.md`、`TODO.md` | 实施并验证后记录实际结果和剩余事项 |

执行顺序为确定 `developing` 的统一规则，更新两个技能的交接，随后同步说明与元数据。每次编辑基于文件当前内容。

## Verification

### 方案一致性检查

- 对照当前三个技能确认每项修改位置，保留已有的有效规则。
- 检查每种进入条件都有适用的交付或返回条件。
- 检查局部修复、可信研究结果和整个任务完成之间的判定。
- 检查范围变化、证据更新、只读要求及上游文档授权能否同时满足。
- 检查 README 和元数据与规范文件表达一致。

### 实施后的真实任务验收

从真实需求和可核实的仓库状态选择符合下列条件的任务，使用实际文件、命令、数据及输出完成验收。

| 任务条件 | 验收要求 |
| --- | --- |
| 用户只要求设计讨论 | 交付所需设计及依据，操作范围符合用户请求 |
| 高影响且设计明确 | 执行已确定方案，具备相应计划、检查与验证 |
| 实施中发现异常 | 诊断后继续原任务，完成剩余要求 |
| 研究结果不支持假设 | 根据有效性证据及研究目标解释结果 |
| 用户要求的性能指标尚未达到 | 正确报告该目标的完成状态 |
| 验证后相关文件被修改 | 根据当前内容重新运行受影响检查 |
| 用户改变任务范围 | 执行符合当前要求的剩余工作 |
| 只读诊断或研究 | 交付证据与结论，文件操作遵守只读要求 |
| 多个子代理返回成果 | 主代理核验关键结果，完成必要整合与验证 |

格式与引用检查使用实际技能文件和现有校验工具。方案一致性检查、格式检查和真实任务执行分别报告；只有实际运行的项目才能记录为已验证。
